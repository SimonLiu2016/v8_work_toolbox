## Context

见 `proposal.md - Why`。这里只记录决定修法的事实。

**触发路径实测**（本机，115 轮 / 8 槽位的中英对照会议）：

```
说话人 3 有 53 轮 → 续句合并后约 40 组
一次下拉 = 40 次 TTS
  顺：1-3 分钟
  卡：单次 90s 超时 × 重试 2 次 → 最坏 40 × 270s
```

期间 `_busy = true` 冻结整个页面，`_realProgress` 无值，`_speakers` 未刷新。

## Goals / Non-Goals

**Goals:**

- 改设置是瞬时的：点完立刻看到新值，不需要等
- 用户随时知道"我听到的是旧音色还是新音色"
- 重新合成可中断、可取消，失败不毁已有音频

**Non-Goals:**

- 不做后台任务队列（应用退出即中断）
- 不改 TTS 端点的重试与超时
- 不引入"改音色前先试听一段"

## Decisions

### D1：设定立即生效，合成为显式动作（乙方案）

```
改音色
  ├─ 立即（毫秒级）：写覆盖层 → 刷新 speakers → 下拉回填 → 重建 Clip（时间轴不变）
  └─ 标记：该槽位的组「待更新」，面板显示 N 组
        └─ 用户点「重新合成」→ 进度 + 取消 → 完成才替换音频
```

**备选甲（立刻重烘 + 进度 + 取消）**：设定与音频始终一致，但"改个下拉要等 1-3 分钟"依旧，且每次误点都真的烧 TTS 配额。否决。

**备选丙（只对下次合成生效）**：最安全，但用户改完看不到任何变化，会当成 bug——这正是当前的第二症状。否决。

**代价**：存在"设定是 A、音频是 B"的中间态。用 D2 的可见状态兜住。

### D2：一致性按组记录，`Clip` 的音色字段记"实际"不记"设定"

`TurnGroupAudio` 增加 `voiceId`（这一组实际合成用的音色）。`pendingGroups(meeting)` = 设定解析出的音色 ≠ 组记录音色的那些组。

`Clip.turns[].voice` 在重建时 MUST 取**组记录的实际音色**，而不是当前设定：

```
   rebuildAudio 组装 Clip
        │
        ├─ 组有 voiceId 记录  → 用它（这是听得到的那个声音）
        └─ 组无记录（旧数据） → 用当前设定音色，且**不算待更新**
```

**为什么旧数据不算待更新**：升级后把所有历史会议都标成"待更新"是恐吓式提示，用户什么都没改。缺失记录只意味着"不知道当时用的什么"，不该被当成"用错了"。

**为什么 Clip 记实际而非设定**：`Clip` 是派生产物，`voice` 字段的语义是"这段音频是哪个声音"，用于追溯（spec: 音色分配可追溯）。记设定会让"追溯"变成"猜测"。

### D3：重新合成不删原件，成功才替换

现在的 `_resynthesizeSlot` 是"先删后建"。改成：

```
为待更新的组合成 → 写到 g<k>.new.mp3
   成功 → rename 覆盖 g<k>.mp3，state.voiceId 更新
   失败 → 删除 .new，保留旧 g<k>.mp3，该组仍待更新
```

**为什么用临时文件而不是直接覆写**：`_synthesizeToFile` 本身在失败时不会产出文件，但一旦轮到"写静音占位"分支就会盖掉旧音频。临时文件 + rename 把"破坏"与"成功"绑定在一起，是唯一不依赖调用方细心的做法。

### D4：取消按组边界生效

`rebakeGroups` 接受 `bool Function() shouldCancel`，只在**组与组之间**检查。取消后：已完成的组保留新音频，未完成的保持待更新，然后照常重建整篇（时间戳会因新音频时长不同而变化，本来就要重算）。

**为什么不中途打断单组**：一次 TTS 请求中途取消只会留下半截临时文件，没有收益。

### D5：忙碌状态按操作分域

`_busy` 拆成三个互不影响的标志：

| 标志 | 影响 | 谁在等 |
|---|---|---|
| `_importing` | 禁用「导入逐字稿」 | 解析 + 首次合成 |
| `_baking` | 禁用「生成音频」 | 补烘缺失素材 |
| `_rebaking` | 禁用「重新合成」 | 重烘待更新组 |

改设定不属于任何一类——它是即时的，不再有忙碌状态。

**为什么值得拆**：现在是"一处卡住，全页禁用"，而这三种操作彼此独立。拆开后「生成音频」跑着 40 分钟时，用户仍能改设定、仍能导入下一份文稿。

### D6：下拉框乐观更新

面板的 `value` 取自 `speakers`，而 `speakers` 由页面按当前设定解析。改设定后页面立即 `_loadRealMeetings()`（纯本地 IO，毫秒级），下拉随即回填。

不再依赖"合成完成"这个远在几十分钟后的时机。

## Risks / Trade-offs

- **用户改完音色没听到变化就以为没生效** → 面板显示「N 组音频待更新（当前仍是旧音色）」，并提供一键重新合成
- **待更新组数与实际听感不一致**（续句组跨说话人） → 组是合成单位，标记也以组为准，与音频实际分段一致
- **取消后时间戳变化** → 重建整篇时重算，点轮定位仍以重算结果为准
- **旧数据无 `voiceId`** → 不标待更新；首次重新合成后补齐。若用户确实想换音色，改设定后该组自然进入待更新
- **`_rebaking` 与 `_baking` 同时触发** → 两者都会重建整篇音频，需串行化（同一会议的音频重建加锁或排队）

## Migration Plan

无数据迁移。`TurnGroupAudio.voiceId` 为新增可选字段，旧文件缺省为空，按 D2 处理。

回滚：还原代码即可；已写出的 `voiceId` 对旧版本是未知字段，JSON 解析会忽略。
