## Context

动机与行为契约见 proposal.md 与本次 change 的五份 spec delta。这里只记录实现层面的关键约束。

当前三条相关路径的取材与指代现状：

| 路径 | 参考图来源 | `<Picture N>` |
|---|---|---|
| 生关键帧 | `_referenceImages()`（`studio_generation_tasks.dart:85`）三级回退：形态三视图 → `turnaround.png` → `referenceImages.first` | 无（用自然语言「第N张图作为…」） |
| 分镜级视频 | `VideoGenTask` 自己写的一份：`referenceImages.first` → `faceAnchorPath` | **完全没有** |
| 片段级视频 | `SegmentVideoGenTask` 自己写的一份：`referenceImages.first` | 有，但只在顶部锚点段 |

三份取材逻辑互不一致，且都不读用户意图（没有任何 UI 能表达意图）。`maxReferenceImages` 能力声明已存在（`media_capability.dart:89`，语义 0/null/正数），设置页也能显示，但 Agnes 适配器硬编码 `5` 且**静默 `take(5)`**。

## Goals / Non-Goals

**Goals:**

- 让分镜成为素材指代的唯一来源：用户声明 → 编号 → 提示词 → 提交数组，全链路一致。
- 分镜级与片段级共用同一套取材与指代编译，消除三份不一致的逻辑。
- 让「谁对着谁」进入视频提示词（`gazeTarget` 首次被视频侧消费）。
- 参考图上限从模型能力声明读取，超限报错而非静默截断。
- 清空本集分镜时物理媒体真正离场。

**Non-Goals:**

- 不做旧 `storyboard.json` 自动迁移——用户将清空重测。无绑定的分镜读取时按空绑定处理，不猜。
- 不改 IP 主库的素材生成能力（三视图/七方位视角/面部锚点如何产出）。
- 不改配音流水线顺序。`<Audio N>` 只立契约，默认不传、UI 不暴露。
- 不解决「视频模型仍不遵守已正确给出的时序/注视」——那是模型能力问题。

## Decisions

### 1. 素材绑定放在分镜上，不做全局默认表

```
方案 A：分镜上存 assetBindings（选定）
方案 B：角色卡上设「默认用于生成的素材图」，分镜不存
```

选 A。B 看似省字段，但它无法表达「同一角色在不同镜头用不同素材」——比如第 1 镜用劲装三视图、第 8 镜换成常服三视图，这是真实需求。A 把选择权放在分镜，角色卡的「默认值」只作为新建绑定时的初值。

```
StudioShot.assetBindings: Map<String, ShotAssetBinding>
  key: 角色卡 id 或场景卡 id
  ShotAssetBinding {
    String materialPath;      // 相对资产目录的文件名；空串 = 用系统默认
    ShotRole role;            // subject / confrontation / supporting（仅角色有意义）
  }
```

`materialPath` 允许为空串是刻意的：用户不想逐镜指定时，系统取默认并在 UI 展示「取了哪张」。一旦用户改过，就是确定值。

**为什么不复用 `characterVariations`**：那个字段是「形态」语义（驱动生图的服装差异词），与「用哪张图」是两个关注点。混在一起会让「换形态」和「换素材」互相干扰。

### 2. 编号由绑定表生成，不靠名称匹配

片段级现有的 `references.indexWhere(r => r.usage.contains(name))` 有两个问题：名称互相包含时会错配（「老王」vs「老王头」），且依赖调用方额外传一份 `references` 列表。

新方案：绑定表本身有序（按插入序），编号 = 绑定在有序列表中的下标 + 1。提示词编译与提交数组从同一个有序列表产出，**编号错位在结构上不可能发生**。

```
有序绑定列表 = [姜七夜(c1), 老王(c2), 衙门(s1)]
                    ↓ 1        ↓ 2        ↓ 3
提交数组       = [姜图,       王图,       衙图]
提示词行       = 姜七夜动作（<Picture 1>）
                 老王台词（<Picture 2>）
```

`<Picture N>` 与 `{{ref N}}` 两套写法统一为前者——adapter 的 payload 就是 `images[]` 数组，官方文档用的是 `<Picture N>`。既有 `{{ref N}}` 只存在于注释与测试断言中，无实际消费方。

### 3. 空间关系编译成「相对关系」而非「绝对方向」

现状：`screenPosition` 是「画面右侧面向左」这类描述，`gazeDirection` 是「面向北门警惕注视」这类向量。两者都是**单角色绝对描述**，模型要自己推导二人的相对关系。

新编译输出相对关系：

```
【空间关系】
姜七夜立于衙门口内侧偏左，面朝画面右，目光聚焦于老王；
老王立于姜七夜右侧一丈处，面朝画面左，目光聚焦于姜七夜；
二人相对对峙，视线在中线交会。
```

规则：
- 分工含 `confrontation` 且同镜有两个及以上角色 → 编译相互注视；
- `gazeTarget` 非空 → 写「目光聚焦于X」；为空 → 不编造；
- 单角色镜 → 只写该角色自身的位置与朝向，不出现他人。

**为什么不直接透传台账原文**：台账是给人和 AI 拆镜看的字段，粒度与措辞都不针对视频模型。「画面右侧面向左」对模型是噪声，它需要的是「面朝右、看着老王」。

### 4. 时间流水：编号进每一行，片段级串成一条

现有【因果时间轴】已解决单镜内先后（上一轮 change）。本次做两件事：

```
1. 每行带素材编号
   0.0s-2.3s 姜七夜拱手一拜（<Picture 1>）
   2.3s-3.8s 姜七夜转身牵驴向门口（<Picture 1>）
   3.8s-5.0s 老王跳脚，老王台词（<Picture 2>）

2. 片段级串成一条连续流水
   [0.0s-4.0s] 镜号1：姜七夜拱手（<Picture 1>）
   [4.0s-7.0s] 镜号2：姜七夜转身（<Picture 1>）+ 老王台词（<Picture 2>）
   [7.0s-12.0s] 镜号3：老王跳脚（<Picture 2>）
```

片段级复用 `CausalityTimelineCompiler.cumulativeRanges`（上一轮已抽），首镜从 0.0 起算，末镜结束 = 片段目标时长。

### 5. 参考图上限：读能力声明，超限阻止

```
现在：video_gen_adapter.dart:1145
  if (derivedMode == 'reference' && refUris.length > 5) refUris.take(5)
  → 静默截断，台账记的却是提交值，用户以为约束生效了

改成：
  final maxRefs = capability.maxReferenceImages;
  if (maxRefs != null && refUris.length > maxRefs) {
    throw StateError('当前模型最多支持 $maxRefs 个参考素材，本次提交了 ${refUris.length} 个。'
        '请在分镜的出场资产中减少角色或场景。');
  }
```

同时在 UI 侧提前警告：分镜卡在绑定数超过当前模型上限时显示警告条（用户已定「给用户提示，让用户手动处理」）。

`media_capability.dart` 中 Agnes 视频型号的 `maxReferenceImages` 按型号填写：`agnes-video-2.5` 为 8，`agnes-video-2.5-flash` 为 5。两个型号不冲突，各自声明即可。

该数值 SHALL 同时开放界面设置，使用户可在能力声明与实测不符时自行修正——供应商调整上限时不必等发版。能力声明的职责从「写死一个正确数字」变为「给出一个可改的初值」。

**为什么不在 UI 侧截断**：截断等于替用户决定放弃哪个角色，而那正是导致「人物被换掉」的同类错误。阻止 + 明示，让用户自己减。

### 6. 清空归档：接上已有函数，补 audio/

`archiveEpisodeMedia`（`studio_project_manager.dart:292`）已实现，覆盖 `clips/`、`frames/`、`segments/`，但**全仓库无调用方**。改动：

```
1. _confirmAndClearAllShots 里，saveEpisode 之后调用 archiveEpisodeMedia
2. archiveEpisodeMedia 的 subDirs 增加 episodeAudioDir
3. exports/ 不加（成片是交付物，文件名固定会被覆盖，不构成幽灵）
4. 弹窗文案与 SnackBar 告知归档位置
```

**为什么不直接物理删除**：用户可能只是想重新拆镜，旧视频是花了算力成本的。归档保留可追溯，同时从制作目录移除以杜绝幽灵。

### 7. 分镜卡面板布局

现有分镜卡已有：场景、角色、形态、模式、画幅、时长、景别、情绪等控件，卡片已很长。新增「出场资产」面板采用折叠式：

```
┌─ 出场资产 ───────────── [展开/收起] ─┐
│ 角色  [+ 添加]                       │
│  姜七夜  主体[▾]  [turnaround.png ▾] │
│  老王    对峙[▾]  [turnaround.png ▾] │
│ 场景                                 │
│  衙门            [view_front.png ▾]  │
│ ⚠ 已选 6 个素材，当前模型上限 5 个   │
└──────────────────────────────────────┘
```

默认收起，展开时才占空间。原「角色」与「形态」两行移入该面板（形态从属于角色，本就不该与角色并列）。

若实际占位仍过挤，退路是把整个面板改为弹窗：卡片上只留一行摘要（「2 角色 · 1 场景 · 6/5 素材」+ 一个「配置」按钮），点击展开弹窗。这个退路不改数据与编译层，只改承载容器，因此可以后置到实测观感后再决定。

## Risks / Trade-offs

- **[Risk] 面板改动大，与现有控件争夺卡片空间** → **[Mitigation]** 折叠式默认收起；原「角色」「形态」行移入面板而非并列新增，净增高度可控。
- **[Risk] 两条路径统一取材后，已生成片段重跑时画面会变** → **[Mitigation]** 用户将清空重测；且新行为（按绑定取材）比旧行为（硬取 `.first`）更可预期。
- **[Risk] 静默截断改报错后，历史能跑的多资产分镜被阻止** → **[Mitigation]** UI 侧提前警告 + 明确提示上限；这是用户明确要求的「让用户手动处理」。
- **[Risk] `materialPath` 为空串时的「系统默认」仍是猜** → **[Mitigation]** 默认规则在 UI 上可见（展示选了哪张），用户可覆盖；且默认规则与生图路径同源，不会再出现两条路径猜得不同。
- **[Risk] 供应商调整参考图上限后，代码里的声明数字过期，拦住合法请求** → **[Mitigation]** 该数值在界面可改，用户实测不符时自行修正即可，不必等发版。

## Migration Plan

无数据迁移。旧分镜的 `assetBindings` 缺失时按空绑定处理：不传该分镜的任何参考图，由 C11 之外的既有校验或「缺参考图」提示拦住。用户将清空重测，因此不保留兼容路径。

回滚策略：素材绑定是指令式新增字段，回滚即恢复旧取材逻辑；提示词编译与 adapter 改动的回滚不影响已生成产物。
