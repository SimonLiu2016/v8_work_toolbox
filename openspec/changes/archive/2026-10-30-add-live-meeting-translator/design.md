## Context

见 proposal.md - Why。此处只记录**直接约束实现方式**的实测事实与既有能力。

**本机实测（2026-10-22）**：

- `ffmpeg -f avfoundation -list_devices` 列出本机音频设备，其中 `Soundflower (2ch)` 与 `Soundflower (64ch)` 已安装可用，可直接作为系统输出的内录目标。
- 仓库既有 `ffmpeg_composer` / `ai_subtitle_service.dart` 已有 FFmpeg 路径探测逻辑，可复用。
- StepFun ASR 仅提供 **HTTP + SSE** 一种流式方式（`/v1/audio/asr/sse`），**无 WebSocket**、**无说话人分离**、文档未提 VAD。SSE 事件为 `transcript.text.delta` / `transcript.text.done` / `error`；`enable_timestamp=true` 时事件带 `start_time`/`end_time`（毫秒）。
- 请求音频为 base64 PCM（16kHz / 16-bit / 单声道），支持 `hotwords`、`language`、`enable_itn`。

**仓库可复用的既有能力**：

- `lib/tools/lookup_panel/ui/lookup_window.dart` — 透明无边框置顶浮窗的现成原型（`Colors.transparent` + 原生层圆角）。
- `lib/main.dart` 的 `WindowKind` 枚举与 `WindowServices.required` 显式服务清单，以及 `itListeningMini` 作为"第三种窗口形态"的先例。
- `macos/Runner/AppDelegate.swift` 已有 Carbon `RegisterEventHotKey`（⌥D/⌥S）与 `NSStatusItem` 托盘的现成用法。
- `AiConfigStore` 的槽位机制（`text` 用于翻译，`stt` 用于识别）与有序候选健康回退。
- `desktop_multi_window` 子窗口 + `WindowController` 跨窗口通信。

## Goals / Non-Goals

**Goals:**

- 识别链路低延迟且成本可控：本地 VAD 挡掉静音、分块带重叠避免切词、SSE 增量文本边出边显。
- 状态集中在主进程，悬浮窗只做视图——与 it-listening 的 D7 同构，避免跨 isolate 状态分裂。
- 说话人手动切换为主路径：零成本、零准确率风险，导出时用户可核对修正。
- 翻译不阻塞识别：定稿句触发翻译，与后续句识别并行。

**Non-Goals:**

- 不做自动说话人分离（StepFun 不支持，第三方 API 贵）。
- 不做本地离线 ASR（延迟不可接受）。
- 不做麦克风输入捕获。
- 不做 WebSocket ASR（StepFun 无此能力，不为它引入第二家 ASR 供应商）。
- 不做自动记录（记录由用户显式开始/停止）。

## Decisions

### D1: 内录走 FFmpeg + Soundflower，不写原生 loopback

**决策**：用 FFmpeg 子进程以 `avfoundation` 捕获选定的虚拟声卡设备，输出 16kHz 单声道 PCM 到 stdout，由 Dart 侧消费为字节流。

**理由**：本机已装 Soundflower 且被 ffmpeg 正确枚举；仓库已有 FFmpeg 路径探测与子进程管理经验；零原生代码、零新依赖。用户已确认"针对我当前的电脑设计就行"，接受在系统音频设置里把输出切到 Soundflower。

**备选与取舍**：*原生 AudioServerPlugIn loopback* 免虚拟声卡但要写 Swift 插件、权限复杂；*ScreenCaptureKit*（macOS 13+）免驱动但仅 13+、需屏幕录制权限、音视频捆绑。两者成本都高于本方案，留作未来迁移路径。

### D2: 本地 VAD 用能量阈值，分块固定 2s + 0.5s 重叠

**决策**：对连续 PCM 流按短帧（如 20ms）计算 RMS 能量，超过阈值判为语音。语音段按约 2 秒切块，相邻块重叠约 0.5 秒。

**理由**：StepFun 无 VAD，本地必须先挡静音，否则静音也发请求既慢又费额度。能量阈值实现简单、零依赖、对会议语音（语速均匀）足够。2s 块兼顾首字延迟与识别完整度，0.5s 重叠避免词被块边界切断（重叠区由下游去重）。

**备选与取舍**：*WebRTC VAD* 更准（能区分清浊音）但需引入原生库；*不分块整段流式*StepFun SSE 不支持持续推流（每次请求带一段音频），必须切块。首版用能量阈值，实测误判再升级。

### D3: ASR 客户端是"请求-响应式 SSE"，非长连接流式

**决策**：每个音频块发起一次 SSE 请求（`POST /v1/audio/asr/sse`），消费该请求的 delta/done 事件后关闭。块与块之间的请求由上层串行或有限并发调度。

**理由**：StepFun SSE 的语义是"提交一段音频→流式返回该段识别结果"，不是"建立长连接持续推音频"。把它建模为每块一次请求最贴合协议，也最易做超时与重试。重叠区带来的重复文本由下游按时间戳去重合并。

**备选与取舍**：*维护长连接模拟真流式*与协议不符且难做错误恢复；*一次性提交整段*失去实时性。按块请求 + 上层节流（如识别未返回就不发下一块，或限并发 1-2）即可达到"准实时"。

### D4: 识别状态在主进程，悬浮窗是纯视图

**决策**：音频捕获、VAD、ASR 请求、翻译、字幕记录与导出全部在主进程；字幕悬浮窗是独立子窗口，只订阅字幕快照并渲染，通过 `WindowController` 接收推送与发送指令（切换说话人、清空、调字号）。

**理由**：与 it-listening 的 D7 同构。`desktop_multi_window` 子窗口是独立 isolate，若把 ASR/翻译放子窗口，主窗口管理界面就拿不到状态，且悬浮窗关闭会中断识别。放主进程则两者都满足：悬浮窗可随意开关，识别不中断，主窗口设置与记录管理始终有真实状态。

**备选与取舍**：*悬浮窗自持识别*会牺牲状态一致性与"关窗不中断"；*跨 isolate 事件总线*需要额外抽象，`WindowController` 已是现成机制。

### D5: 说话人 = 手动热键切换的具名槽位

**决策**：维护固定数量（首版 3 个）的说话人槽位，每个有名字与固定颜色。全局热键 ⌥1/⌥2/⌥3 切换"当前说话人"，此后定稿的字幕归到当前槽位。

**理由**：StepFun 不支持 diarization，手动切换是零成本零风险的正解，也符合用户在 Zoom/Teams 里的既有习惯。颜色与槽位固定绑定，保证一场会议内角色可辨。

**备选与取舍**：*自动声学聚类*首版不做（复杂度高、会议音质下准确率不稳）；*第三方 diarization API* 贵且引入新供应商。留作后续可选项，数据模型预留"说话人来源"字段以便将来混用自动与手动。

### D6: 翻译走 text 槽位，定稿句触发、可工具级覆盖

**决策**：ASR 的 `done` 事件定稿一句 → 立即用 `text` 槽位翻译该句；工具设置里可覆盖翻译用的供应商/模型，覆盖只对本工具有效。译文未返回时原文先显示，返回后补登同一字幕单元。

**理由**：复用系统 AI 配置（用户要求"沿用系统设置，亦可工具单独设置"）。逐句触发与后续句识别并行，翻译 1-3s 的延迟落在会议语音的自然停顿里，可读。原文先显、译文补登避免翻译阻塞字幕实时性。

**备选与取舍**：*整段结束后批量翻译*零实时译文；*流式缓冲边识别边翻*实现复杂且部分文本翻译质量差。逐句是延迟与质量的最优折中。

### D7: 记录内存累积 + 显式导出，SRT/VTT 带说话人与双语

**决策**：仅当用户"开始记录"后，定稿的字幕单元累积在内存；"停止记录"后可导出。SRT 每条为 `[说话人] 原文 / 译文` 两行，VTT 用 `<v 说话人>`  voice 标签。时间轴用识别记录的起止毫秒，暂停期间不产生字幕故时间轴天然连续。

**理由**：用户明确选择"手动开始/停止记录"（选项 B）。不落库、不自动持久化，最简单且无数据迁移负担。音频不落盘，字幕只在导出时写文件。

**备选与取舍**：*自动录音*会产生不可控累积与磁盘占用；*存 SQLite* 需要加表与迁移，而导出是终点消费，内存足够（一场会议几百条）。SRT 双行 + VTT voice 标签都是标准兼容写法。

### D8: 悬浮窗复用 lookup_window 的透明窗口机制

**决策**：字幕悬浮窗复用查词浮窗的窗口配置（透明、无边框、置顶、不抢焦点），只替换内容区为字幕渲染 + 控制条。拖动通过窗口级手势移动整个窗口。

**理由**：透明置顶是已验证可行的现成能力，避免重踩"透明通道被不透背影盖掉"的坑（lookup_window 的注释已记录该坑）。内容区独立，不影响窗口层机制。

**备选与取舍**：*新建一套窗口配置*会重复踩透明/圆角的坑；*复用播放器小窗*形态不符（那是音乐条，这是字幕区）。

## Risks / Trade-offs

- **Soundflower 需用户在系统音频设置里切换输出** → 首版面向用户本机，接受一次性设置；管理界面提供设备选择与"未捕获到音频"的明确提示（spec 已覆盖降级）。
- **能量阈值 VAD 在嘈杂环境下误判** → 阈值做成可调；误判的代价只是多几次无效请求，不会出错字幕。实测噪声环境再考虑升级 WebRTC VAD。
- **SSE 每块一次请求，延迟 = 块长 + 网络 + 识别** → 首字延迟约 2-4s（用户已确认可接受）；块长与重叠做成常量便于后续调；增量 delta 事件让块内文本先于 done 显示，掩盖部分延迟。
- **重叠区重复文本** → 下游按 `start_time` 去重合并，丢弃与上一块时间重叠且文本重复的片段；去重失败的最坏结果是字幕偶有重复词，不致命。
- **翻译依赖 text 槽位可用性** → 翻译失败 MUST NOT 影响原文显示与导出（spec 的"译文为空不阻塞"已覆盖）；译文缺失时导出只含原文。
- **识别中途网络中断** → 自动重连 + 连续失败停止并提示（spec 已覆盖），已定稿字幕不丢。
- **API Key 失效（鉴权失败）** → spec 要求可归因错误提示；`stepfun` 供应商纳入既有健康检查与回退链，主候选失败可回退到 `stt` 槽位的其它候选。
- **子窗口 isolate 状态同步复杂度** → 只做"主进程持有全部状态、悬浮窗渲染 + 双向 invokeMethod"一条路径，不做通用跨窗口框架（与 it-listening D7 一致）。

## Migration Plan

无破坏性变更。全部为新增：

- 新增工具目录 `lib/tools/live_translator/`
- `lib/tools/registry.dart` + `tool_definition.dart` 新增注册与标识常量
- `lib/main.dart` 新增 `WindowKind.liveCaption` 与子窗口分支
- `lib/services/ai_config_store.dart` 新增 `stepfun` 协议类型
- `macos/Runner/AppDelegate.swift` 新增菜单栏项与说话人切换/字幕开关热键
- `lib/services/app_paths.dart` 新增字幕导出目录登记
- **无数据库迁移**（字幕仅内存累积 + 按需导出文件）

回滚：移除注册表条目、`WindowKind` 分支与 AppDelegate 热键即可，无残留数据依赖。

## Open Questions

- 能量阈值 VAD 的具体门限（dB 或 RMS 绝对值）需在真实会议音频上标定——实现时先给默认值并暴露为可调项，实测后再定默认。这不影响 spec 与任务拆分。
- 重叠区去重的精确算法（按文本前缀/后缀匹配 vs 纯时间戳丢弃）待联调时按 StepFun 实际返回的 `start_time` 粒度确定。
