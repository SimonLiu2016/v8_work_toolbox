## Context

见 proposal.md。`_joinSegments` 是为上一轮 change 的时序序列新增的拼段辅助函数，位于 `prompt_assembler.dart` 的 `PromptAssembler` 内，被 `_joinWithinLimit` 复用——而 `_joinWithinLimit` 同时服务 `buildShotPrompt` 的正向段与负向词列表、`buildSegmentPrompt` 的全部段。

这意味着 `_joinSegments` 的口径会影响**三个消费方**：生图正向、生图负向、片段视频。这是当初引入它时未充分考虑的面。

## Goals / Non-Goals

**Goals:**

- 块结构段（多行时序序列）前后都断行。
- 单行段之间保持既有的「, 」口径，不生变化。
- 负向词列表恢复逗号分隔（它是逐词列表，不是段）。

**Non-Goals:**

- 不重构 `_joinWithinLimit` 的双重职责（既管长度裁剪又管拼接）。那是独立的坏味，但不影响本次正确性。
- 不改任何提交给模型的语义内容。

## Decisions

### 1. 判据改为「前一段或本段含换行」

```
现在：breakBefore = 前一段含换行
改成：breakBefore = 前一段含换行 || 本段含换行
```

```
段序列：[风格, 运镜, 锚点, 时序块(多行), 声音约束]

  前一段多行？   本段多行？   分隔符
  ─────────────────────────────────────
  风格→运镜      否           否       ", "
  运镜→锚点      否           否       ", "
  锚点→时序块    否           是       "\n\n"   ← 本段多行，块前断行
  时序块→声音    是           否       "\n\n"   ← 前段多行，块后断行
```

**为什么不用「本段是不是时序块」这种语义判据**：那要把「什么是块结构」的知识塞进拼段函数，而它只应关心文本形态。含不含换行是块结构的充要特征，且不需要引入新概念。

### 2. 不动负向词路径的调用方式

负向词列表（`buildShotPrompt` 的 `negativeTokensList`）经同一个 `_joinWithinLimit` 输出。修正判据后，由于每个负向词都是单行且不含换行，`breakBefore` 恒为 false，输出自动恢复「, 」——**不需要为负向词单独开一条拼接路径**。

这一点是选「文本形态判据」而非「语义判据」的额外收益：语义判据（如「本段是时序序列吗」）对负向词同样返回 false，也能work；但文本判据更简单，且不依赖调用方传标记。

### 3. 两条遗留断言的同步口径

```
「剥离对白台词与剧本标头，锁定主物理场景，机位协调」
  → 改名「对白保留为时间区间内的配音行，剧本标头被剥离，锁定主物理场景，机位协调」
  → 断言：台词不再被剥，改断言「对白：<原文>」存在
           动作不再被逗号平接，改断言「动作：<原文>」分行存在
           补一条：含对白时必须有声音与画面约束（全员闭口守卫）

「目标时长不泄露进提示词文本，动作自然整合」
  → 不动（它断言的是时长数字不出现，与本次无关，仍然成立）
```

**为什么不删掉这两条测试**：它们锁的是真实契约，只是断言口径停在旧行为。删掉会丢掉覆盖；同步口径才保住意图。

## Risks / Trade-offs

- **[Risk] 换行分隔可能影响既有的「片段提示词不含换行」类假设** → **[Mitigation]** 已确认无此类断言；`_wordsOf` 以 `\n` 为切分符之一，长度统计不受影响（反而更准——按行计数比按整段计数更接近真实 token）。
- **[Risk] 负向词恢复逗号后，某条依赖换行的既有断言可能红** → **[Mitigation]** 全量跑过 `test/agnes_studio_pipeline_test.dart` 等五个文件，73 项全通过。

## Migration Plan

无数据迁移。纯提示词拼装口径与测试断言同步，回滚即恢复旧判据。
