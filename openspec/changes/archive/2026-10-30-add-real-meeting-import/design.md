## Context

见 `proposal.md - Why`。这里只记录决定方案形态的现状与约束。

**现有管线**（`lib/tools/it_meeting_listening/`）：三条来源最终都收敛到 `Clip`（`id / scene / title / audioPath / durationMs / turns / source / summary`），`turns` 是 `SpeakerTurn`（`speaker / role / rawText / synthesisText / voice / startMs / endMs`）。播放器按 `clip.audioPath` 播单文件、按 `turn.startMs` 定位。

**必须复用的既有经验**：`RehearsalBaker` 已经有「逐轮合成 → 写中间 mp3 → concat → 按实际音频时长回填时间戳」的完整实现，以及对着 TTS 端点斗出来的四条防线（空音频重试、HTTP 451 降级到 120 字碎片、HTTP 402 配额 fast-fail、900 字切分）。真实会议是同一类问题（长、多轮、多音色），应当照搬而不是另起一套。

**样例实测**（`20261020-ai-agent-security-review/逐字稿_原文_20261020.md`）：

| 事实 | 数值 | 对设计的影响 |
|---|---|---|
| 轮次 / 时长 | 152 轮 / 20分6秒 | 整场一次合成约 3-6 分钟，需续跑 |
| 说话人槽位 | 6 个（`发言人 1..6`） | 槽位数不等于人数，不自动合并 |
| 跨说话人断句 | 59/152（39%） | 逐轮合成会在半句处换声 |
| 时间戳 | 单调、中位间隔 7s | 可直接作为轮次时序，不需要对齐音频 |
| 分隔符 | `U+00A0` | 按普通空格解析会得到 0 轮 |
| 英文 token / 不同词 | 2782 / 633 | 词表规模小，全量内存索引可行 |
| 噪声词 | `aCRI`、`theCLI2`、`Zest's`、`ABD` | 词表需要噪声折叠 |
| 中文残留 | 12 轮 / 207 字 | 音色池本身是中文 TTS，照常合成即可 |

**约束**：用户侧没有原始录音，音频一律由 TTS 合成；不做 LLM 修稿（会污染词频）；`itMeetingListeningCacheDir` 会被界面的「清理缓存」`clearTurnCache` 清空。

## Goals / Non-Goals

**Goals:**

- 真实会议以一种与既有两类内容同构的形态进入素材库，复用播放器、热键、断点、变速，不改这些组件
- 原稿不可变：改名、音色、插入回答都是可删除的覆盖层
- 插入回答的音频成本是「只合成新增那一段」，与会议长度无关
- 词表在应用重启后可全量重建，且与增量维护结果一致

**Non-Goals:**

- 不做逐轮音频的语音识别校验（现有 `whisper small` 校验只服务于合成失败检测，不引入到这条链路）
- 不做跨会议去重（同一场会导入两次是用户的错，用内容哈希兜住即可）
- 不做词形还原（`deploy` / `deployed` / `deploying` 各自计数，只做大小写与所有格归一化）

## Decisions

### D1：真实会议作为第三类内容，沿用 `Clip` 模型

`MeetingScene` 增加 `realMeeting`，`ClipSource.sourceId` 取 `real-meeting`，与 `rehearsal` 同构。逐字稿的结构化结果（说话人槽位、覆盖层、回答层）**不塞进 `Clip`**，而是单独存，`Clip` 只承载"能播的那一份"（整篇音频 + 轮次 + 时间戳）。

**为什么**：播放器、索引、热键、断点、连续播放全部依赖 `Clip`。新造一套素材模型意味着这五样各写一遍。`Clip` 只要求"一条音频 + 一组带时间戳的轮次"，整场会议刚好满足。

**备选**：把真实会议做成独立工具页。否决——用户要的是同一个播放器、同一套练习习惯，独立页会分裂热键与断点。

**代价**：`Clip.turns` 是展示用的投影，真实来源在 `real_meetings/meetings/<id>.json`。两者可能短暂不一致（例如覆盖层改了名字但 `Clip` 没重写）。约定：**`Clip` 是派生产物，每次会议数据变更后由 `RealMeetingStore` 重建并写回索引**，不反向依赖。

### D2：三层分离——原稿 / 覆盖层 / 回答层

```
meetings/<id>.json     原稿：槽位、轮次、时间戳、关键词。导入后只读
settings/<id>.json     覆盖层：槽位 → 显示名 / 音色 / 是否"我"。可整层删除
answers/<id>.json      回答层：锚点轮、提问轮、身份、英文、中文原文、音频
```

**为什么**：三者的生命周期不同。改名是一次轻量操作，不该触发重解析；插入回答要能撤销；重新导入改过的文稿时，原稿必须被替换，但用户设定的名字应该还在。合在一个文件里，"重新导入"就只能整体覆盖，用户改的名字全丢。

**备选**：全塞进 `Clip` 的 JSON。否决——`Clip` 被索引文件全量引用，插一段回答就要重写整个索引。

**锚点选择**：回答层锚定在**轮次下标**而不是时间戳。时间戳在插入之后会平移，下标不会（原稿只读）。文稿内容变化时下标可能越界，此时该回答标记为失效（spec 已约束）。

### D3：续句合并在合成层，展示与索引保持原样

判定规则是纯函数：`turn[i]` 若首字符为非大写字母，且 `turn[i-1]` 的正文不以 `.` `?` `!` 结尾，则并入 `turn[i-1]` 所在组，组内统一用 `turn[i-1]` 的说话人音色。

产出是一个 `groups: List<List<int>>`（轮次下标的分组），**不改动任何 `SpeakerTurn`**。`Clip.turns` 仍是 152 轮；只有送 TTS 的文本按组合并，时间戳按组回填后**组内各轮共享该组的起止毫秒**。

**为什么**：展示层是用户核对"会上到底说了什么"的唯一依据，任何合并都是信息损失；而音频层半句换声是最刺耳的瑕疵。两层分开，两边的目标各自满足。

**代价**：组内后几轮明明可能是另一个人说的，却被算到组首说话人头上。这是无真值下的必然损失，规则选的是"听觉连续性优先"。

**备选**：按标点重建轮次边界再重新分配说话人。否决——那是修稿，已列为非目标。

### D4：逐轮音频持久化，重建只做 concat

逐轮 mp3 落在 `real_meetings/turns/<id>/t<i>.mp3`（**不在 `itMeetingListeningCacheDir`**）。插入回答 = 合成新段落到同一目录（如 `answer_<n>.mp3`）→ 按"原稿轮次 + 回答锚点"生成拼接顺序 → `ffmpeg concat` → 重探各段时长 → 重算时间戳。

**为什么**：`RehearsalBaker` 本来就是逐轮写文件再 concat，中途把文件放缓存目录只是当时的实现选择。真实会议一旦清了缓存，插入就要重跑 450 轮 TTS——那是十分钟的等待。移到持久目录后，插入的边际成本是"合成 1 段 + concat 20 秒音频"。

**代价**：磁盘占用。20 分钟会议约 152 个小文件（~96kbps 下 1-3MB）；60 分钟约 10MB 级。可接受，且比整篇重烘便宜得多。

**备选**：插入后整篇重烘。否决（见上）。**备选**：不 concat，播放时切文件。否决——要改播放器内核，且总时长与 seek 语义都要重做。

### D5：词汇索引是 JSON 快照，不是数据库

`vocabulary_index.json` 存两级结构：`perMeeting: {meetingId: {word: count}}` 与倒排 `postings: {word: [{meetingId, turn, speaker, startMs, text}]}`。

**为什么**：样例 633 个不同词 / 场，即使 50 场会议也只有万级词条、十万级 postings，`jsonDecode` + 建索引在百毫秒级。项目里虽然有 drift（`notebook.db`），但引入 schema 迁移的成本远大于收益。`perMeeting` 这一层让"删除一场会议"变成"删掉一个 key"，不需要重扫文稿。

**降级**：索引文件缺失或损坏时，从 `meetings/*.json` 全量重建（spec 已要求重建结果与增量一致）。

**备选**：drift 表。否决——当前规模不值得一个 schema。

### D6：噪声折叠不依赖在线词典

判定 = 「全语料出现 ≤ 1 次」∧「不在内置停用词表（约 100 词，硬编码）」∧「不在该会议「关键词」段」。三者同时成立才折叠。

**为什么**：`lookup_panel` 的词典是网络服务（`dictionary_service`），离线不可用，而"这词是不是真英文"必须在导入时立刻给出。会议记录系统自己产出的「关键词」段是一个现成的、用户可见的真术语白名单——实测那份文稿的 10 个关键词全部是真实术语。

**代价**：只出现一次的**真**低频词（如某个版本号）会被折叠。可展开、可手动标为正常词，且查询时永远返回结果（spec 已约束）。

### D7：AI 上下文用"标题 + 前序窗口 + 目标轮"，不整篇送

送 LLM 的内容 = 会议标题 + 关键词 + 被选中轮之前最多 N 轮（N 取能填满预算的最大值，预算约 6000 token）+ 被选中轮本身。整篇不送。

**为什么**：样例 20 分钟会议约 11k 英文字符，整篇可送；但 60 分钟会议会到 40k 字符，且其中大半与"这一问该怎么答"无关。窗口送法既省 token，又天然把"上下文"限定成真正相关的那段。截断时明确告知用户截掉了什么（spec 已约束）。

**备选**：先让 LLM 摘要整场再问答。否决——多一次调用一次成本，且摘要会丢细节，而回答恰恰需要细节。

### D8：「我的身份」与排练会议 Simon 共用一个音色

`my_identity.json` 存 `{name, voiceId}`，默认 `{name: "我", voiceId: "boyinnansheng"}`——`boyinnansheng` 正是 `RehearsalVoices` 给 `simon` 的绑定。

**为什么**：两个功能里的"我"在用户心里是同一个实体。音色不同会让用户困惑"为什么我的声音变了"。默认值直接抄排练会议的绑定，零配置即可用。

**备选**：让用户先配置再导入。否决——首次使用就被拦在配置页是不可接受的摩擦。

### D9：界面落点

```
听力练习（工具页）
├─ 素材库        公开素材 · 排练会议 · 真实会议   ← 类型筛选，第三类在此
├─ 真实会议      导入 / 会议列表 / 逐字稿练习（按轮定位 + 选段回答）
└─ 词汇表        跨会词频 + 反查                  ← 跨会议，不挂在任何一场上
```

**为什么**：逐字稿的按轮定位与说话人设定不属于任何单个 `Clip`；词汇表更是跨全部会议的。把两者塞进现有的"场景 → 片段 → 播放"导航会让同一份数据出现在错误的层级。

## Risks / Trade-offs

- **TTS 会念出 ASR 错字**（`In ABD, in a zoo, right?`）→ 已明确接受（非目标）。缓解：疑似噪声词在词汇表主列表不展示；用户可对单轮重试合成，但不能改文本（改文本等于修稿）
- **续句合并会把某人的话算到别人头上** → 展示层保留原样，用户能看到真实归属；合并规则是纯函数、可关闭、可重算
- **长会议合成耗时与配额**（450 轮，HTTP 402 可能中途出现）→ 续跑 + 失败轮可见 + 402 fast-fail 不在失败轮上重试
- **词表随时间膨胀** → JSON 全量读写是 O(语料)。若单场会议超过 5000 个不同词或总会议数超过 100，需改为按会议分片加载。当前规模（633 词/场）留了 8 倍余量
- **与在途 change 的 spec 冲突**：`add-meeting-material-rehearsal` 已在 `it-meeting-listening-tool` 上声明「素材库容纳两类内容」。本 change 声明「素材库容纳真实会议导入」。两者 archive 时需合并为"三类"，先归档者先落，后归档者按三类改写
- **覆盖层与 `Clip` 投影不一致** → 约定 `Clip` 是派生产物，任何会议数据变更后由 `RealMeetingStore` 重建并写回索引，不反向依赖

## Migration Plan

无历史数据需要迁移（新增内容类型，既有 `Clip` 与索引结构不变，`ClipSource.sourceId` 对旧数据缺省 `coderslingo` 的容错已存在）。

回滚：删除 `real_meetings/` 与 `vocabulary_index.json`，索引中 `sourceId == 'real-meeting'` 的条目一并移除——不影响既有两类内容。

## 归档时的合并说明

`it-meeting-listening-tool` 目前有一条在途 change（`add-meeting-material-rehearsal`）声明了「素材库容纳**两类**内容」。本 change 额外声明「素材库容纳真实会议导入」。

两者归档时间不同，合并规则：

- 先归档本 change → 主 spec 里出现「两类内容」+「真实会议导入」两条需求，语义上已覆盖三类，后续归档排练会议时按三类改写它的那条。
- 先归档排练会议 → 它的「两类」先落，本 change 的「真实会议导入」作为追加需求直接叠加，归档后需把排练会议那条从「两类」改成「三类」。

无论哪种顺序，**「按类型筛选」的能力只应有一条需求**，不要留下两条各自描述筛选项的重复条款。
