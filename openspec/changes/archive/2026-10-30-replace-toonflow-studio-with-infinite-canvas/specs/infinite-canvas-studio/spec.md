## Purpose

Docker 托管的无限画布工作台生命周期管理。本 capability 覆盖 Compose 工程定位、容器启停、健康就绪判定、端口分配与冲突预检、运行时配置注入、镜像入口与失败诊断、工作台入口，以及应用退出时的容器处置。本工具不实现任何无限画布创作能力——创作在无限画布自己的工作台里完成。

无限画布与 Toonflow 的关键差异决定了本 spec 的形状：它的 docker 镜像只是一个 nginx 静态服务器（`nginx:1.27-alpine` + Vite 产物），没有任何业务 API、没有任何数据卷。因此健康判据必须从「校验业务接口的 JSON 信封」反转为「校验静态容器标识」，数据目录与 bind mount 整条需求消失，而端口回环从部署细节升格为安全需求（上游 `compose.yaml` 默认把 3000 绑到全部网卡）。

## ADDED Requirements

### Requirement: Compose 工程定位

系统 SHALL 通过一个可配置的目录定位无限画布的 Docker Compose 工程，该目录必须同时包含 `Dockerfile` 与一个 compose 文件。系统 SHALL 接受 `compose.yaml`、`compose.yml` 与 `docker-compose.yml` 三种文件名，因为上游仓库实际提供的是 `docker-compose.yml`。默认值 SHALL 为 `~/Workspace/github/infinite-canvas`，用户可在工具界面修改，修改后 SHALL 持久化。

系统 SHALL 在工程目录不存在、或目录中缺少上述任一文件时报告明确的定位失败原因，而不是尝试运行 Docker 命令。系统 SHALL 同时报告它实际找到的 compose 文件名，因为 override 文件必须与它对齐。

#### Scenario: 默认工程目录存在

- **WHEN** 用户首次打开无限画布工具，且 `~/Workspace/github/infinite-canvas/` 下 `Dockerfile` 与 `docker-compose.yml` 均存在
- **THEN** 系统使用该目录作为工程目录，不要求用户输入任何配置

#### Scenario: 工程目录缺失

- **WHEN** 配置的工程目录不存在，或目录中缺少 `Dockerfile` 或三种受支持的 compose 文件中的任何一种
- **THEN** 系统报告定位失败，指出具体是哪一个条件不满足，并引导用户修改工程目录配置

#### Scenario: 用户修改工程目录

- **WHEN** 用户把工程目录改为另一个包含 `Dockerfile` 与 compose 文件的有效路径并保存
- **THEN** 后续所有容器操作都作用于新目录，且重启应用后该配置仍然生效

### Requirement: 容器启停与状态呈现

系统 SHALL 支持启动与停止无限画布容器组，并向用户呈现当前状态。启动流程 SHALL 包含守护进程探活、端口预检与健康就绪等待三个步骤，只有在服务真正就绪后才报告「运行中」。

系统 SHALL 在启动失败时保留失败原因，供用户修正后重试，而不是静默回到未启动状态。系统 SHALL 在引擎已在运行时忽略重复的启动请求，保持当前运行状态。

#### Scenario: 启动成功

- **WHEN** 用户在服务未运行时触发启动，且 Docker 守护进程可达、端口无冲突、镜像已存在、服务在就绪超时内通过健康探测
- **THEN** 系统报告「运行中」，状态区展示工作台地址，并提供打开工作台的入口

#### Scenario: 停止

- **WHEN** 用户在服务运行时触发停止
- **THEN** 系统停止容器组并报告「已停止」；若停止过程本身失败，系统报告失败原因而不是假装已停止

#### Scenario: 重复启动

- **WHEN** 服务已在运行时用户再次触发启动
- **THEN** 系统不重复执行启动，保持当前运行状态

### Requirement: 健康就绪判定必须校验静态容器标识

系统 SHALL 通过 HTTP 探测判定服务就绪。判定 SHALL 校验响应体是无限画布容器的入口页面，仅 HTTP 状态码为 200 不足以判定就绪。

判据 SHALL 同时要求响应体包含两项标识：SPA 挂载点 `<div id="root">`，以及指向 `/config.js` 的 script 标签。`/config.js` 由容器 entrypoint 在启动时按环境变量生成，因此它的存在同时证明「这是我们容器的 nginx 而不是宿主机上另一个占着端口的服务」且「entrypoint 已执行完毕」。

此要求的原因是：无限画布的 docker 容器**只有**静态资源，没有任何业务 API，nginx 的 `try_files` 回退规则会对任意路径返回 200 的 `index.html`。只看状态码会把「另一个进程占用了这个端口」误判为「无限画布已就绪」，把用户送到一个打不开的工作台。

#### Scenario: 服务真正就绪

- **WHEN** 健康探测收到 200 且响应体同时包含 `<div id="root">` 与指向 `/config.js` 的 script 标签
- **THEN** 系统判定服务已就绪

#### Scenario: 收到 200 但是别的服务

- **WHEN** 健康探测收到 200 但响应体不含上述两项标识（例如宿主机另一个进程占用了该端口）
- **THEN** 系统判定未就绪，继续等待直到超时，并在超时后报告「服务未返回预期的健康响应」而不是「已就绪」

#### Scenario: entrypoint 尚未执行

- **WHEN** 健康探测收到 200 且响应体含挂载点但不含 `/config.js` script 标签
- **THEN** 系统判定未就绪，继续等待——容器刚拉起、entrypoint 还没跑完时打开工作台会因缺运行时配置而不完整

#### Scenario: 就绪超时

- **WHEN** 启动后在就绪超时内健康探测始终未通过
- **THEN** 系统报告启动失败，附上容器最后若干行日志以便定位

### Requirement: 端口分配与冲突预检

系统 SHALL 为无限画布的 HTTP 端口提供可配置值，默认可由实现选定但 SHALL NOT 与本软件已托管的其他引擎端口（ARTEX 的 8787 与 8788、本地词典桥的 8797）冲突。

端口映射 SHALL 只绑 `127.0.0.1`。此要求的原因是：上游 `compose.yaml` 的默认写法是 `"3000:3000"`，绑到全部网卡，等于把工作台暴露给同局域网的所有人——而工作台的浏览器本地存储里存着用户的 API Key。

系统 SHALL 在启动前侦测该端口在宿主机是否已被占用；被占用时启动失败，报告被占用的端口号，并允许用户修改端口后重新启动。

#### Scenario: 端口空闲

- **WHEN** 配置端口在宿主机可绑定
- **THEN** 系统继续启动流程

#### Scenario: 端口被占用

- **WHEN** 配置的 HTTP 端口已被其他进程监听
- **THEN** 系统在启动前报告启动失败，指明端口被占用，且不启动容器

#### Scenario: 用户改端口后重试

- **WHEN** 用户把冲突端口改为空闲值并重新触发启动
- **THEN** 系统使用新端口完成启动，且就绪判定与工作台入口都指向新端口

#### Scenario: 本软件自己的服务端口不算冲突

- **WHEN** 启动前侦测发现某端口由本软件的另一个服务（资产桥）持有
- **THEN** 系统不把它报告为端口冲突，工作台正常启动——该端口的可用性由持有它的服务自己判定并报告

### Requirement: 运行时配置以 override 注入而不修改上游工程文件

系统 SHALL 通过独立的 Docker Compose override 文件注入运行时配置，而不是编辑工程目录中的 compose 文件。override SHALL 至少承担两项职责：把端口映射覆盖为用户配置的回环端口，以及在需要时覆盖镜像引用。

override 文件的生命周期由系统管理：内容随配置变化而更新，与上游工程文件互不影响，因此上游工程升级（如 `git pull`）不会丢失这些配置。系统 SHALL 在重写已存在的 override 文件前确认该文件由本工具生成（以标记注释识别），非本工具生成的文件 SHALL 先备份而不是直接覆盖。

override SHALL NOT 注入 bind mount，SHALL NOT 注入 `user:` 对齐。此要求的原因是：无限画布的容器是 nginx 静态服务器，不写任何数据目录，这两项在 Toonflow 上是必需的、在这里是无意义且会让 override 更难读的噪音。

#### Scenario: 首次生成 override

- **WHEN** 系统首次为某工程目录启动无限画布，且该目录中没有 override 文件
- **THEN** 系统生成 override 文件，其中包含回环端口映射

#### Scenario: 端口配置变化

- **WHEN** 用户修改端口配置
- **THEN** 系统更新 override 文件中的端口映射，使下次启动使用新端口

#### Scenario: 上游工程升级后配置不丢

- **WHEN** 上游 compose 文件被更新或替换
- **THEN** 系统生成维护的 override 文件内容保持不变，端口映射继续生效

#### Scenario: 用户手工编辑的 override 被备份

- **WHEN** 工程目录中已存在 override 文件但缺少本工具的生成标记
- **THEN** 系统备份该文件后写入自己的 override，而不是直接覆盖用户内容

### Requirement: 镜像入口与失败诊断

系统 SHALL 以拉取远端镜像为默认路径启动容器，因为上游 `docker-compose.yml` 引用 `ghcr.io` 上已发布的双架构镜像。

系统 SHALL 提供触发本地构建的可选入口，以流式方式向用户呈现构建进度。本地构建仅在用户要跑自己改过的代码时才需要，SHALL NOT 是启动的必经步骤。

系统 SHALL 对构建失败做模式识别，把已知失败类别转换为可操作提示，而不是把构建工具的原始输出直接呈现给用户。至少 SHALL 识别四类：Docker 守护进程不可达、镜像源返回 403、网络请求超时、构建上下文缺失。

#### Scenario: 默认走拉取

- **WHEN** 用户触发启动且本地没有镜像
- **THEN** 系统从远端拉取镜像并完成启动，不要求用户先点「构建」

#### Scenario: 构建进行中

- **WHEN** 用户触发构建
- **THEN** 系统以流式日志呈现构建进度，构建期间禁止重复触发

#### Scenario: Docker 未运行

- **WHEN** 触发构建或启动时 Docker 守护进程不可达
- **THEN** 系统报告「Docker 未运行」并提供跳转到 Docker 应用的方式

#### Scenario: 镜像源 403

- **WHEN** 构建输出中出现镜像源返回 403 的失败
- **THEN** 系统提示镜像加速器失效，引导用户检查或移除 Docker 的镜像源配置

#### Scenario: 网络超时

- **WHEN** 构建输出中出现请求超时或连接被取消
- **THEN** 系统提示网络不通，引导用户检查代理或 VPN，并说明已完成的构建层有缓存、重试不会从零开始

#### Scenario: 构建锁冲突被避免

- **WHEN** 构建进行中用户再次触发构建
- **THEN** 系统不发起第二次构建，而是复用当前构建的进度，不产生两个并发的 `docker compose build`

### Requirement: 打开工作台与容器未就绪时的引导

系统 SHALL 在服务就绪后提供打开工作台的入口，使用系统默认浏览器打开 `http://127.0.0.1:<配置端口>`。

工作台入口 SHALL 仅在服务就绪时可点击；未就绪时系统 SHALL 说明当前阻塞原因（未启动 / 启动中 / 失败及原因）。

#### Scenario: 就绪后打开工作台

- **WHEN** 服务状态为运行中且用户点击「打开工作台」
- **THEN** 系统用系统默认浏览器打开配置端口对应的工作台地址

#### Scenario: 未就绪时入口不可用

- **WHEN** 服务状态为未启动或启动中
- **THEN** 系统禁用「打开工作台」入口，并展示当前状态与阻塞原因

### Requirement: 应用退出时的容器处置

系统 SHALL 提供「退出时是否停止容器」的配置项，默认值为停止。系统 SHALL 在应用进程收到终止信号或主窗口关闭时按该配置处置容器，且 SHALL NOT 因为停止容器失败而阻塞应用退出。

#### Scenario: 默认退出即停

- **WHEN** 用户未修改过该配置，且无限画布容器正在运行时应用退出
- **THEN** 系统停止容器组后退出，不留下继续占用端口的孤儿容器

#### Scenario: 用户配置为退出不停

- **WHEN** 用户把该配置改为退出时不停止，且容器正在运行时应用退出
- **THEN** 系统不停止容器，容器继续在后台运行，用户下次打开工具时能直接看到运行中状态

#### Scenario: 停止失败不阻塞退出

- **WHEN** 应用退出时停止容器失败或超时
- **THEN** 系统仍然完成退出，不无限期等待，并在日志中记录停止失败
