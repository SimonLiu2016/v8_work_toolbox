## Context

见 proposal.md - Why。此处只记录**实测得到、且直接约束实现方式**的事实。

### 既有播放体系（可复用）

`it_meeting_listening` 已有完整的播放外壳：常驻迷你窗（`it_listening_mini_player.dart`）、全局热键（⌃⌥Space/C/B/1/0）、断点记忆、四档变速、按句高亮的精听面板、术语收藏。排练会议只需要**进入这套体系**，不需要重写。

### 既有烘焙管线（可复用）

`ClipBaker` 已实现逐轮合成 + 三道防线，都是上一轮实测踩坑后加的：

| 防线 | 触发条件 | 行为 |
|---|---|---|
| 空音频重试 | 端点返回 0 字节 | 重试 2 次 |
| 内容审查降级 | HTTP 451 censorship_blocked | 切到 120 字碎片重试 |
| 配额 fast-fail | HTTP 402 quota_exceeded | 立即放弃，不重试 |
| 超长切分 | input > 900 字 | 按句子边界切，单句超长按词硬切 |

排练会议是**超长剧本**（140-280 轮），这四道防线一个都不能少。

### 角色与音色池

现有音色池 9 个，实测 F0 分过性别：男声 6 个、女声 3 个。5 个角色全为男性，从 6 个男声里取 5 个。

**注意**：`step_boy` 实测 207Hz 是**女声**（名字骗人），所以不能用。可用男声为：`boyinnansheng`(130)、`dushexiaoyu`(129)、`ruyananshi`(126)、`cixingnansheng`(119)、`shenchennanyin`(136)。

### 材料格式与既有解析能力

用户材料为 MD/HTML。仓库已有：
- `DocumentParser._parseMarkdown` —— MD 解析（`reader/services/document_parser.dart`）
- `htmlToMarkdown(String html)` —— HTML 转 Markdown（`services/html_to_markdown.dart`）

### 规模实测依据（2026-10-22）

```
轮次        140          280
烘焙耗时    6 分钟       11 分钟
音频大小    1.9 MB       3.8 MB

```

## Goals / Non-Goals

**Goals:**

- 材料（MD/HTML）能导入并解析为可供 LLM 分析的结构化文本
- 生成 Simon 第一人称的英文讲稿，按议题分节，节与语音一一对应
- 生成 5 角色、四段结构、30-60 分钟的模拟会议剧本
- 会议按回合切分音频并与文本对应，整场连续可播
- 排练会议进入既有播放体系（悬浮窗/热键/断点/变速/按回合定位）
- 5 角色音色固定且可区分

**Non-Goals:**

- 不做 PDF/Word 导入（格式约定 MD/HTML）
- 不做实时流式合成
- 不做影子跟读打分
- 不做云端同步/分享
- 不改 `EdgeTtsEngine`
- 不改既有 CoderSlingo 素材导入链路

## Decisions

### D1: 讲稿与剧本分两次 LLM 调用，而非一次生成

**决策**：先用 text 槽位从材料生成**讲稿**，再用 text 槽位从「材料 + 讲稿」生成**剧本**。两次独立调用。

**理由**：
- 讲稿是 Simon 的**单人口述**，需要结构化、分议题、保留材料细节
- 剧本是**五人对话**，需要在讲稿基础上演化出追问、质疑、协作补充
- 一次生成会让 LLM 同时处理"内容提炼"和"戏剧化改编"两件事，两边都做不好
- 分两次让讲稿可**单独修改后重新生成剧本**——用户改讲稿是高频操作（会前要调内容），剧本可弃之重来

**备选与取舍**：*一次生成讲稿+剧本*——省一次调用，但耦合了两件关注点不同的事，且讲稿改了就全废。

### D2: 剧本一次生成整场，不分段生成再拼

**决策**：整场剧本由**一次 LLM 调用**生成，然后逐回合合成。

**理由**：
- 会议有弧线（开场→议题→Q&A→收尾），分段生成会丢失跨段呼应（如开场提的议题三要在 Q&A 收尾）
- 一次生成能保证人物立场一致（客户方全程质疑、Huawei 侧全程补充）
- LLM 的 context 装得下 140-280 轮剧本（约 4500-9000 词）

**备选与取舍**：*分段生成再拼*——每次调用短、失败重试便宜，但跨段连贯性差，人物立场可能漂移。

### D3: 音频按「回合」切分，不按「议题段」切分

**决策**：每轮对话（一个说话人的一次发言）一个音频小节。

**理由**：
- 用户要"按回合定位"——点某一轮就从那轮开始播。回合是最自然的定位单位
- 合成失败能定位到**轮**，重试成本最低（一句 vs 一段）
- 与既有 `SpeakerTurn` 模型一致，播放器可直接复用

**备选与取舍**：*按议题段切分*——文件少（5-10 个 vs 140-280 个），但定位粒度粗、重试成本高。

### D4: 整场音频 = concat 所有回合，一条连续 mp3

**决策**：所有回合音频按序 ffmpeg concat 成**一条** mp3，回合起止时间由各小节时长累加得出。

**理由**：
- 用户要"整场播放"——一条文件最简单，播放器无需维护播放列表
- 与既有 CoderSlingo 素材的产物形态一致（都是一个 mp3 + 一个 json 清单）
- 按回合定位靠 json 里的 `startMs/endMs`，不需要物理切分文件

**备选与取舍**：*每回合一个文件 + 播放列表*——定位更直接，但播放器要改造成列表模式，且 280 个文件的 IO 与清理更麻烦。

### D5: 复用 `ClipBaker` 的合成防线，但不复用其切分逻辑

**决策**：新写 `RehearsalBaker`，**复制** `ClipBaker` 的合成重试/审查降级/配额 fast-fail 逻辑，但**不复用** `splitLongTurn`/`segment()`。

**理由**：
- 合成防线是**与端点斗**的经验，必须照搬（否则重新踩 451/402/400）
- 切分逻辑是**为 1-3 分钟碎片设计**的（3 分钟上限、尾段合并），会议需要的是整场连贯，切分逻辑完全不适用
- 会议剧本的单轮通常 < 900 字（LLM 生成的一句话发言），所以超长切分的触发概率低，但**防线仍要保留**（LLM 偶尔会长篇大论）

**备选与取舍**：*直接复用 ClipBaker*——会引入 3 分钟切分，把 30 分钟会议切成 10 个片段，违背"整场"的需求。*把切分逻辑参数化*——改 `ClipBaker` 会影响既有素材链路，风险大于收益。

### D6: 角色音色表硬编码，不做用户配置

**决策**：5 个角色 → 音色的映射写死为常量表，首版不提供 UI 修改。

**理由**：
- 角色是**用户自己定的**（Simon/xiaofeng/songyang/deepan/Josh），不是通用场景
- 音色池只有 6 个男声，可选项极少，配置 UI 的价值低
- 用户要的是"固定、可区分"，硬编码已满足

**备选与取舍**：*做成可配置*——灵活但增加 UI 与持久化成本，且首版用户没有"换音色"的明确诉求。

### D7: 排练会议与既有素材共用 `Clip` 模型，用 sourceId 区分

**决策**：排练会议落盘为 `Clip`（`sourceId: 'rehearsal'`），进入同一份 `index.json`，不新建素材库。

**理由**：
- `Clip` 模型（id/scene/title/audioPath/durationMs/turns/source/summary）完全装得下排练会议
- 共用素材库 → 播放器、悬浮窗、热键、断点、术语收藏**零改动**即可支持
- 新增一个 `MeetingScene.rehearsal` 场景值即可分类

**备选与取舍**：*独立的排练会议存储*——隔离但要让播放器支持两套存储，改造成本高于收益。

**注意**：现有素材的时长上限隐含假设是"1-3 分钟"（`splitLongTurn` 的 900 字、`segment` 的 3 分钟）。排练会议 30-60 分钟会突破这些假设——但这些假设都在 `ClipBaker` 里，而 `RehearsalBaker` 不复用它们，所以不冲突。**唯一要检查的是播放器与 UI 是否有硬编码的时长上限**（实测没有）。

### D8: 讲稿与剧本的生成失败要能分别重试

**决策**：讲稿生成、剧本生成、语音合成是**三个可分别重试**的阶段，每阶段失败不影响其它阶段已有产物。

**理由**：
- 讲稿生成失败（LLM 超时）不该让用户重跑整个流程
- 剧本改了就重跑剧本 → 语音要跟着重烘（剧本变了音频必然变）
- 单轮合成失败只重试那一轮

**备选与取舍**：*一个按钮跑完全程*——省事但任何一步失败都要从头再来。

## Risks / Trade-offs

- **LLM 生成剧本的时长不可控** → 实测 LLM 生成"30 分钟会议"可能给出 5000 或 15000 词。对策：prompt 里给**明确的轮次目标**（如 120-150 轮）而不是"30 分钟"，并在生成后按语速校验，偏离区间时提示用户。**这一条必须在实现时实测**。
- **280 轮烘焙要 11 分钟 + 配额** → 上一轮实测撞过 402。对策：进度可见、可中断、单轮失败不毁整场；单轮 fast-fail 避免配额耗尽后空转。
- **内容审查误判** → 上一轮实测：讲 VPN 密码的 154 字段落被判 451。会议材料若含敏感词（客户纠纷、安全事件）可能触发。对策：已有 120 字碎片降级；仍失败的轮次标记为失败并允许人工改写。
- **材料可能很大** → MD/HTML 可能几万字。对策：导入时按 token 预算截断或分段送 LLM（讲稿生成阶段），并在界面上说明"材料过长时仅分析前 N 字"。
- **音色只有 5 个男声，恰好用完** → 若某个音色被端点下线或审查，没有替补。对策：音色表留一个空位标注为"备用"，失败时能换。
- **LLM 剧本的英文质量** → 非母语 LLM 生成的会议英语可能不自然。对策：prompt 里给真实会议语料的**风格要求**（口语、短句、有 uh/um、有打断），并要求避免书面语。

## Migration Plan

无破坏性变更。全部为新增：

- 新增 `rehearsal_*.dart` 系列文件
- `MeetingScene` 增一个枚举值 `rehearsal`
- 素材索引 `index.json` 新增 `sourceId: 'rehearsal'` 的条目（既有素材不受影响）
- 播放器外壳零改动（已有能力）
- 回滚：删除新文件 + 移除枚举值即可，既有素材目录不受影响

## Open Questions

- 讲稿生成时材料过长如何截断（按 token 预算？按章节？）——实现时先用"取前 N 字 + 提示用户"，观察真实材料规模后再细化。
- 剧本的轮次目标值（120-150 轮？）需实测 LLM 输出规模后校准——**这一条直接影响时长是否达标**，实现时必须跑一次真实生成看词数。
