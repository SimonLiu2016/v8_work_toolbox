## Context

见 `proposal.md` — Why。这里只记约束：

- 故障文本（`() => Null` 不是某函数类型的子类型）只在**运行期**成立：本次已全量开启 `strict-casts` 扫过整个 `lib/`，结论是**不存在**任何"隐式降级到函数类型"的静态点；`audioplayers` 6.7.1 / `audioplayers_platform_interface` 7.1.1 / `flutter_secure_storage` 9.2.4 三包**全无裸 `Function`**。也就是说，靠继续静态推断找不到它。
- 抛错位置被 `catch` 吞掉，只留 `$e.toString()` 进 UI，不写日志。实测出错那次在 `logs/ai.log` **零痕迹**。
- 播放分支的覆盖现状：`test/it_meeting_listening/vocabulary_player_and_transcript_scroll_test.dart` 有 4 处构造用例，其中 3 处注入 `audioPlayerFn`，1 处不注入但只断言文本/筛选——**真实播放分支从未被执行**。
- 三条入口（单词发音 / 句子发音 / 连续磨耳朵）共用同一段播放代码，但**失败文案前缀不同**（"发音生成失败"vs"发音失败"），语义上却都覆盖了合成与播放两个阶段。

## Goals / Non-Goals

**Goals:**

- 让下一次复现**一次就能拿到**抛错位置：异常类型、消息、堆栈，同时进 UI 与日志。
- 让"播放一次音频文件"的真实编排逻辑（停止 → 播放 → 等待完成/超时）成为**被自动化测试真实执行**的代码。
- 把失败语义按阶段拆开，使"合成失败"与"播放失败"不再互相伪装。

**Non-Goals:**

- 不改 TTS 合成引擎与供应商解析（已验证非故障点，且合成日志显示成功）。
- 不引入新的播放器依赖，不升级 audioplayers。
- 不新增词汇表的功能（重点关注、句子翻译等一律不动）。
- 不追求一次扫清全仓既有 `strict-casts` 报错（那是独立议题，见 Decision D4 的缓解）。

## Decisions

### D1: 用"运行期可观测性"钉死抛错行，而不是继续推断

**选择**：在播放链路的捕获点落地**完整异常 + 堆栈**（UI 显示异常类型与消息摘要，日志写全量含堆栈）；同时把 `strict-casts` 纳入门禁（见 D4）作为防回归。

**理由**：静态面已被本次扫描穷尽（无静态降级点、依赖包无裸 `Function`、`Future.timeout` 的 `onTimeout` 实测无害），剩余可能只能是运行期才成立的路径——例如平台通道边界、版本差异或动态槽位。这类问题只能靠运行时捕获定位。

**已否决的替代**：
- 继续读代码推断 —— 已证伪到极限，继续只是猜。
- 让用户手抄完整报错 —— 不可靠、不可重复，且界面可能截断。

### D2: 注入接缝必须放在**编排之下**，而不是替换编排

**选择**：定义一个只做**设备操作**的薄后端接口（创建/停止/播放/完成事件流），生产实现是对 `AudioPlayer` 的**无逻辑**包装；播放**编排**（顺序、超时上限、失败处理、连播步进）留在上层业务代码里，测试用假后端真实执行该编排。

**理由**：现状的 `audioPlayerFn` 是"整段替换播放逻辑"，这恰好把生产分支排除在测试之外——接缝位置错了。把接缝降到设备边界，替换的是**设备**而不是**逻辑**，"停止→播放→等待完成/带超时上限"这些真正会抛错的行才能被测试执行。

**已否决的替代**：
- 维持 `audioPlayerFn` 整段替换（现状）—— 覆盖盲区原样保留，等于没修。
- 用假 `AudioPlayer` 子类替换 —— `AudioPlayer` 构造会触发平台通道创建，子类仍继承该副作用，测试里需要额外绕开，脆弱且语义混乱。
- mock audioplayers 的平台通道 —— 保真度最高，但让测试绑死插件的通道协议，跨版本易碎；且它验证的是插件的正确性，不是我们的编排。

**实测印证（本轮实现阶段得到）**：在 widget 测试里**不注入任何替身**、直接走真实播放分支（并预置缓存音频以复刻生产条件）时，`AudioPlayer.stop()` 会卡在
`await creatingCompleter.future`——`FakeAsync` 下平台通道不回复，该 Future 永不完成，测试**既不抛错也不失败，只是静默空过**。这正面坐实了「真实分支在测试中无法被执行」，也正是 4.1 依赖 2.1–2.3 的原因：只有把接缝降到设备边界，播放编排才会真正跑完并可断言。

### D3: 失败语义按阶段拆开

**选择**：合成阶段与播放阶段分别捕获，文案与日志都标明**阶段 + 异常类型 + 消息**（日志含堆栈）。

**理由**：现状两个 catch 的范围相同、前缀却不同，等于用一个笼统措辞掩盖阶段信息——这也是本次只能"知道炸了、不知炸哪儿"的原因之一。

**已否决的替代**：单一 catch（现状）——用户与日志都无法区分阶段，排查成本高。

### D4: 门禁纳入 `strict-casts`，但分批

**选择**：把 `strict-casts` 作为门禁开启；若全量开启噪声过大，则先限定在听力/阅读/TTS 相关目录。

**理由**：这类"编译期静默放行、运行期才炸"的错误，正是 `strict-casts` 的设计目的。本次全量扫描实测会新增约 **47 处既有报错**（集中为 `dynamic` 赋给具体类型的 `argument_type_not_assignable` / `invalid_assignment`，与本次故障无直接关系），故需分批而非一刀切。

**已否决的替代**：不开启 —— 新增的隐式降级会继续静默通过，同类 bug 会以同样方式复发。

## Risks / Trade-offs

- **[根因尚未确证]** → 把"确证抛错行"作为修复前的**硬前置**任务；D1 的埋点就是为了拿到它。在拿到堆栈前不猜测着改播放代码。
- **[4.1 依赖 2.x，顺序不可颠倒]** → 实测证实：未经接缝改造时，「不替换播放实现」的测试会因平台 Future 永不完成而**静默空过**（不失败、也不覆盖）。必须先做接缝再做覆盖测试；**不要写一个看似覆盖实则空过的测试**——那比没有测试更糟。
- **[接缝改造横跨三条入口]** → 三条入口本就共用实现，改一处覆盖三处；但必须回归三条入口各自的手感（单词、句子、连播），并把"共用同一实现"固化进 spec 场景。
- **[故障仅在缓存命中路径出现]** → 本地音频已缓存时 `synthesizeOrGetTtsFile` 提前返回、不发请求也不写日志（本次据"日志零痕迹"推断出的关键事实）。测试必须**同时**覆盖"缓存命中"与"实时合成"两条路径，不能用假合成器把缓存路径掩盖掉。
- **[`strict-casts` 分批带来的不一致]** → 未纳入门禁的目录仍可能有隐式降级；在门禁配置旁写明当前覆盖范围与后续推进计划，避免"以为已开"。
- **[改动可能只治标]**：若最终抛错来自某个上游依赖的版本行为，本地修复只能收敛表现。缓解：确证后判断是"改我们的调用方式"还是"锁依赖版本"，并在 tasks 中单列。

## Migration Plan

无数据迁移、无配置迁移。回滚即回退本次提交；`strict-casts` 若以独立提交引入，可单独回退。
