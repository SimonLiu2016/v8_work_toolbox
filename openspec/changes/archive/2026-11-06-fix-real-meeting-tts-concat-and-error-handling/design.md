## Context

详见 `proposal.md`。真实会议音频合成依赖 `RealMeetingBaker`、`FfmpegAudioToolkit` 与上游 `TtsEngine`（如 MiMo Chat Audio）。当轮次长度超过 900 字符时，话轮被切分为多段，多段合并以及最终全场各组拼接均依赖 `_audio.concat`。

## Goals / Non-Goals

**Goals:**
- 修复长文本分段拼接时的 ffmpeg 失败问题，使 9 组超长话轮能够 100% 成功合成。
- 解决由于不同格式音频混杂导致的整篇音频拼接失败，保证整场会议即使有个别话轮因外部不可抗力失败，整篇音频依然能平滑生成且正常播放。
- 结构化捕获并透出合成失败原因（丢弃原先无意义的写死文案），并在 UI 界面呈现明细与针对性操作入口。

**Non-Goals:**
- 不重构上游各个 TTS 厂商的协议层（如强制 MiMo 改用其他 endpoint），在应用层提供普适的格式防御与转码适配。
- 不修改真实会议原稿数据结构（原稿 `meetings/<id>.json` 继续保持只读）。

## Decisions

### 1. `FfmpegAudioToolkit.concat` 引入自适应重编码回退机制
- **决策**：拼接时优先尝试快速流拷贝（`-c copy`）；当 ffmpeg 退出码非 0（例如遇到 `Invalid audio stream`、PCM 与 MP3 混流等容器/编码不匹配）时，捕获错误并自动使用 `-c:a libmp3lame -b:a 128k` 进行重编码拼接回退。
- **替代方案考虑**：
  - *无条件全量重编码*：对于全量已是合法 MP3 的场景会增加 10~15 秒 CPU 开销。先 copy 后转码回退兼顾性能与 100% 成功率。
  - *仅在检测到 WAV 时转码*：probe 每个文件的开销较大，且 ffmpeg concat list 可能包含数十乃至上百个文件，通过 try-copy-fallback 架构最简洁且覆盖所有未知格式冲突。

### 2. 结构化保留各话轮失败原因并在状态层持久化
- **决策**：
  - 在 `TurnGroupAudio` 中新增可选字段 `failureReason`；
  - `RealMeetingBaker` 在捕获到 TTS 错误（如内容审查、配额耗尽、网络超时）或分段拼接异常时，将具体的异常描述写入该组，并保存到 `MeetingBakeState`；
  - `rebuildAudio` 时仅在 `audioFile.length() > 0` 时认定整篇音频就绪，避免 0 字节损坏文件误报。
- **替代方案考虑**：
  - *仅打印到终端 log*：用户在前端界面无法感知，问题依然卡死。

### 3. 界面展示失败轮次明细并提供明确引导
- **决策**：
  - 当 `failedGroupCount > 0` 时，在真实会议详情概览区域展示醒目的失败警告卡片，列出失败的话轮索引、发言人和具体失败原因；
  - 提供“重试失败组”及“重新拼接整篇音频（修复音频）”操作，支持单独解决拼接或 TTS 问题。

## Risks / Trade-offs

- **[转码耗时增加]** → 仅在快速拷贝失败时触发 libmp3lame 重编码，耗时在 1~3 秒以内，用户几乎无感知。
- **[历史已生成的 0 字节损坏音频]** → 在重新烘焙或点击“修复音频”时，先清理旧的 0 字节文件，重新走稳健拼接流生成有效 MP3。
