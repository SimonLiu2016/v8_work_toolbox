## Context

在大模型输出限制与长篇短剧规划需求的交汇处存在天然矛盾：
1. 算力物理限制：主流大模型供应商及其中转 API（如 Agnes-cn/OpenAI/DeepSeek 等）对单次 HTTP 调用的 `completion_tokens` 通常实施 **4096 Tokens** 的硬上限限制；
2. 戏剧信息量：一个符合高品质要求的短剧分集条目（含篇章名、吸睛标题、30~50 字核心危机冲突、登场角色列表、20~40 字反转留钩、时长等 7 项字段）平均消耗 140~160 Tokens；
3. 大集数需求：长篇小说改编短剧通常规模在 60~120 集（例如用户当前规划的 60 集）。一次性请求 60 集需要消耗 8,000~10,000 Tokens，在第 26~30 集处必然耗尽 4096 Token 上限被切断（`finish_reason: "length"`），造成 JSON 损坏且重试亦无法自愈。

## Goals / Non-Goals

**Goals:**
- **消除 Token 截断崩溃**：无论是 60 集、80 集还是 120 集，所有单次大模型 API 调用的输出 Token 严格控制在 2000~2500 Tokens 安全区间内，彻底消灭 `finish_reason: "length"`；
- **真实独立高能分集**：每一集保持独立推演，具备独特核心冲突与集尾反转钩子，绝不使用机械插值克隆或 `(节拍 X)` 污染后缀；
- **底层解析健壮性与自愈**：增强 `parseJsonLoose` 数组截断自动修复能力，即便因突发情况（网络中断或极端 Token 耗尽）被腰斩，也能自动抢救截断前已完整输出的全部集数条目；
- **流式阶段进度显化**：在研讨室提供细粒度的推演进度提示（大幕架构 -> 第 1 幕细化 -> 第 2 幕细化...），提升用户等待体验。

**Non-Goals:**
- 不修改底层大模型供应商或服务代理的硬件级 Token 参数；
- 不改变 `StudioEpisode`、`StudioSeries` 等已有工程数据库与文件存储结构。

## Decisions

### 1. 两阶段按大幕分批推演管线 (Two-Stage Hierarchical Batching)
- **阶段一（全季宏观大幕规划）**：调用 `StudioAiTask.writersRoomMacroArcs`（或轻量规划请求），仅让模型推演 3~6 个宏观篇章大幕（`macro_arcs`，包含序号、篇章名、集数范围如 `1-15`、核心对抗、转折爆点）。单次输出仅需 ~400 Tokens，100% 极速稳定。
- **阶段二（篇章内分批细化）**：
  - 若目标集数 `<= 20 集`（短篇或实验），走单次快速直出通道；
  - 若目标集数 `> 20 集`（中长篇），根据阶段一的大幕划分，按每个大幕范围（或每批 12~16 集）依次调用大模型推演具体分集。请求时带入当前大幕的主题与前一幕的尾部转折作为承接上下文，单次输出控制在 1800~2200 Tokens；
  - 随后按序聚合合并，得到完整的 60~120 集高保真大纲。
- *替代方案比较*：
  - *方案 A（单次请求压缩字段）*：仅让模型输出标题和一句话，牺牲了极其重要的断章悬念钩子与角色清单，严重损害后续生图与剧本工作流质量，故否决；
  - *方案 B（12~16 骨架插值）*：之前采用过，导致连续 4~5 集完全重复，用户体验极差，已被明确废弃。

### 2. 松散 JSON 数组截断自动修复算法 (parseJsonLoose Repair)
- 当 `jsonDecode` 解析失败且文本包含未闭合的 `episodes: [` 数组时：
  - 从文本末尾向前倒查最后一个完整对象的闭合大括号 `}`；
  - 截取到该位置，安全追加 `\n  ]\n}`，尝试重新解析；
  - 成功后即可直接挽救已成功生成的 N 集数据，避免抛出 `ConstraintParseError`。

### 3. 可观察的推演进度回调 (`onProgress`)
- 在 `planWritersRoomSeasonBeats` 中支持 `void Function(String message, double progress)? onProgress` 参数；
- `WritersRoomDialog` 绑定此回调，在界面状态条中实时显示：
  - `0.1`: "正在构建全季 4 大宏观篇章大幕..."
  - `0.35`: "正在推演第 1 幕高能分集 (1~15 集)..."
  - `0.60`: "正在推演第 2 幕高能分集 (16~30 集)..."
  - `0.85`: "正在推演第 3 幕高能分集 (31~45 集)..."
  - `1.0`: "正在推演第 4 幕季终高能分集并聚合..."

## Risks / Trade-offs

- **[多批次请求增加耗时]** → 单次 4096 Token 巨大请求通常耗时 35~40 秒且极易失败；拆分为 4 次轻量批次（每次约 6~8 秒）串行推进，虽然总耗时约 25~30 秒，但通过实时进度反馈使用户感知更连续，且成功率从 0%（必截断）提升至 100%。
- **[跨大幕的情节衔接]** → 在推演后续大幕时，Prompt 显式注入前一幕的 `season_climax` 或上一集的 `hook` 作为前情上下文，保障跨幕因果时序与对抗张力丝滑衔接。
