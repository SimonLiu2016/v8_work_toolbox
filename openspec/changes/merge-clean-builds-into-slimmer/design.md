## Context

「清理构建产物」与「智能磁盘瘦身」当前是两个独立工具，见 proposal.md 的 Why。本设计只解决**如何合并**，不重复说明动机。

现状的关键事实（决定了实现形状）：

- 瘦身的现有三阶段全部是**硬编码已知路径探测**（`~/Library/Developer/Xcode/DerivedData`、`~/.gradle/caches`、`~/Library/Caches/CocoaPods`、`~/Downloads` 大安装包），不递归，所以是瞬时的（`disk_scanner_service.dart` 的 `_scanInstantTargets`，maxDepth=4，每 200 文件 yield）。
- 项目树内的产物（`node_modules`、`build/`、`dist/`）**不落在任何全局共享位置**，必须遍历才能发现。这是本次变更唯一的新能力——**发现**，而不只是把扫描器搬个位置。
- `clean-builds` 的扫描是用户登记 watchlist 后按目录名递归匹配，永久 `delete(recursive: true)`，无安全评级、无管理员权限、无回收可逆。
- `SlimCandidateItem` 是"一个路径一行"的模型，`subtitle` 是自由文本；`_buildCategoryTabs` 已有按 `SlimmerCategory` 的 `ChoiceChip` 筛选体系，可复用作分组筛选的承载。
- 本机实测的性能基线（详见 proposal.md 的 Impact）：剪枝遍历 `~/` 排除 `Library`/`.git` = **88 秒 / 5571 个同名目录命中**；`-maxdepth 8` = 50 秒 / 2390 命中；而按**提议的 Tier A** 实测（`HOME` 下 `maxdepth 3`、7 个 manifest 信号、无剪枝）= **2.5 秒 / 672 个根，去嵌套后 670 个**。同名目录命中数与真实项目根数相差约 8 倍——这是"纯名称匹配"不可行的量化依据。
- 提议的 Tier A 在本机暴露出一个退化用例：`~/` 顶层存在一个裸 `package.json`，导致**整个 `HOME` 被识别为一个项目根**，去嵌套时它会把其他所有根吃掉（671 → 1）。Tier A 因此 MUST 排除 `HOME` 自身作为根，这是由实测推出的约束而非可选优化。

## Goals / Non-Goals

**Goals:**

- 让瘦身工具零配置即可覆盖项目树内构建产物（合并的核心价值主张）。
- 保持瘦身"分级 + 阶段 1 瞬时 <3 秒"的既有响应合同不被破坏。
- 列表规模可控：数百个候选根不得变成数百行列表。
- 不丢失用户在 `clean-builds` 中登记的 watchlist 与产物类型开关。
- 误报受控：目录名相同但不在项目根内的路径不进入候选。

**Non-Goals:**

- 不处理 `ToolCategory.build` 合并后仅剩 KMA 包生成一个工具的分类空置问题（记录为后续事项）。
- 不改瘦身的 AI 研判管线语义：聚合项整体进入既有单条/批量研判，不为项目根设计新的研判协议。
- 不做全盘遍历的"深度模式"开关。若日后需要，应作为独立变更引入。
- 不迁移 `clean-builds` 的运行日志（无持久价值）。
- 不实现跨机器/多用户的发现缓存共享。

## Decisions

### D1: 两层发现分离 —— 浅层 manifest 发现 + 深层产物收集

把"找出项目根"和"在项目根内找产物"拆成两个独立的扫描阶段，用**发现预算换扫描预算**。

```
Tier A 发现（秒级）
  遍历 HOME，maxdepth 3，只读目录名匹配 manifest 信号
  .git / package.json / pubspec.yaml / build.gradle(.kts)
  / Podfile / CMakeLists.txt / go.mod / xcodeproj
  剪枝：Library（全局缓存在阶段 1 已覆盖）、node_modules、.git、build、dist、.gradle
  MUST 排除 HOME 自身作为根（实测：裸 ~/package.json 会让 HOME 吞掉全部其他根）
  → 670 个候选根（本机实测，2.5 秒）

Tier B 聚合（按根设预算）
  对每个根：剪枝遍历，命中目录名 → 收集 (path, size, 技术栈)
  剪枝：不下降进 .git、已命中产物目录自身
  预算：单根时间预算 2–4s + 单根产物数量上限
  超预算 → 标记"未完整"，不静默丢弃
```

**为什么这样：** 上面两个数字的不对称就是架构依据。浅层发现便宜是因为它不读大小、不深入；深层收集昂贵是因为它是真正的工作。把两者合并成一次遍历，就会得到 88 秒那次实测的结果，直接毁掉瘦身阶段 1 的响应预期。

**实测修正（2.5 秒 / 670 根）：** 提案初稿写的"数秒 / 349 根"是用 `maxdepth 2` + 6 个信号、且只枚举了 10 个候选目录得到的，低估了根数量。按最终提议的 Tier A（`maxdepth 3` + 7 个信号、扫整个 HOME）实测是 2.5 秒 / 670 根——耗时仍在预算内，但规模翻倍。分组呈现因此从"优化"变为"必需"：670 个根聚合后不做分组就是 670 行列表。同时实测发现 670 个根里有 **160 个**（24%）在根目录层就直接命中产物，说明 Tier B 的工作量不会因剪枝而缩水到可忽略，预算必须真实生效。

**为什么必须在规格里写死这个分离：** 这是最容易在实现期退化的地方。一个"就顺手遍历一下"的实现会静默地变成 88 秒的全盘扫描，且用户感知是"扫描变慢了"而不是"我写错了"。所以规格（`disk-scanner-async` 的"项目根发现的预算边界"）把它约束为 MUST NOT 无界遍历，并把超预算标记为 MUST 显式上报。

**备选方案：**
- *纯全盘名称匹配*：88 秒且 5571 个命中，其中大量是误报（见 D2）。不可行。
- *只保留 watchlist，不自动发现*：合并就退化成一个改名，用户仍然要手工登记根，核心价值主张落空。
- *只扫固定的几个常见工作目录*（`~/Workspace`、`~/Documents`）：本机验证时 `~/Documents` 恰好有 670 个根中的 20+ 个，但 `~/ClaudeWorkspace`、`~/HAP_Workspace`、`~/IdeaProjects` 这类不在名单里就会漏。硬编码根列表是 `clean-builds` 的老毛病，不该带进来。

### D2: manifest 门控 —— 只在项目根内才算命中

产物目录只有在"位于被识别为项目根的目录下"时才计入候选。这一个约束同时解决误报和速度两个问题：`~/node_modules` 这种裸顶层目录天然被排除，遍历也天然被限制在项目树内。

本机存在实证误报：`~/` 顶层有一个裸 `node_modules` 和一个 `package-lock.json`。纯名称匹配会把它们塞进用户列表——虽然走了废纸篓可逆，但噪音本身就是缺陷，且会训练用户不信任列表。

**代价（明确接受）：** 不在 manifest 工作区里的产物会漏。例如用户在一个没有 `.git`、没有 `package.json` 的临时目录里 build。watchlist 是显式的逃生口（D4）。

**备选方案：**
- *名称匹配 + 启发式过滤*（例如"父目录看起来不像项目就跳过"）：启发式需要维护规则表，边界含糊，误报仍然要靠猜。manifest 是确定性的信号，且本机 670 个根都是从 7 个信号里拿到的。
- *名称匹配 + 安全评级降为 caution*：不解决速度问题，只是把误报从"删了没事"变成"删了有心理负担"。

### D3: 条目粒度 = 项目根聚合，列表层按技术栈分组

规格已定"一个项目根一个条目"，但本机实测 670 个根聚合后仍是 670 行。所以两层：

```
列表行（组）    Flutter / Dart 构建产物   23 个项目 · 4.2 GB   [展开]
               Node 依赖与产物           11 个项目 · 8.7 GB   [展开]
               Gradle / Android           7 个项目 · 2.1 GB   [展开]

展开后的组内    ▼ node_modules  ×5      build  ×8   .dart_tool ×10
              ▸ ~/Workspace/ctf-new/adpt-order        1.2 GB   ☑
              ▸ ~/Documents/mail_tools               860 MB   ☑
```

组是列表行，项目根是组的展开明细，项目根内部产物是组内明细的第二层。

**承载方式：** 复用 `_buildCategoryTabs` 的 `ChoiceChip` 体系做技术栈筛选（把"组"当 chip），组内展开用现有 `ListTile` + `ExpansionTile` 模式，不需要新造 UI 层级。

**为什么不用"每个匹配目录一条"：** 一个 monorepo 递归出 300 个 `build/` 会让"预估释放空间"、AI 逐条研判、保留清单三处一起崩。

**为什么不用"全局按类型分组"**（例如所有 `node_modules` 合并成一个条目）：用户无法判断哪个项目的依赖会被删，也无法做单项目的保留决策。项目根是保留清单的天然粒度——它对应的是一份代码。

### D4: watchlist 降级为补充输入，而非主路径

`clean-builds` 的 `configs`（项目根 watchlist）与 `artifactOptions`（产物类型开关）迁移到瘦身的配置键，语义变为"额外指定项目根"：

- 主路径 = Tier A + Tier B 自动发现，零配置可用。
- watchlist = Tier A 的补充：被列入 watchlist 的根**豁免 manifest 门控**（这正是 D2 的逃生口），且强制进入 Tier B。
- `artifactOptions` 的 9 个开关继续生效，作用于 Tier B 的命中判定。

迁移语义遵循 `settings-storage` 既有约定：复制而非移动、原文件保留、只执行一次、不覆盖用户在瘦身键中的后续修改。`clean-builds` 的迁移表项（`~/.v8_cleaner_config.json` → `config/clean-builds.json`）保持不变，在其后追加一步"从 `clean-builds.json` 复制到瘦身键"。

**为什么保留 watchlist 而不删：** 直接删等于静默丢用户数据（用户登记的根是手工成本），且丢掉了 D2 唯一可控的逃生口。

**为什么不给 watchlist 单独一个"永久删除"快车道：** 回收策略统一走废纸篓（D5），保留一个例外会让删除语义分叉，用户需要在每个根上重新判断安全等级。

### D5: 删除策略统一为废纸篓，移除永久删除路径

构建产物经瘦身的既有回收管线：废纸篓 → 物理校验 → UI 移除。原 `clean-builds` 的 `delete(recursive: true)` 不可逆路径整体移除。

**代价（明确接受）：** 删一个大 `node_modules` 会占满废纸篓，用户需要记得清空废纸篓才真正释放空间。这是"安全可逆"与"即释放"的取舍，统一走可逆一侧，理由是该工具已经为全局缓存、已卸载残留、多版本运行时都选择了可逆，构建产物无理由分叉。

**缓解：** 清理完成对话框报告"已移至废纸篓 N 项 · 释放 X"，并在失败/容量提示处保持既有措辞（`disk-analyzer` 的 Safe disposal 要求未变）。

### D6: 聚合项的稳定身份键 = 项目根路径

`SlimCandidateItem.id` 使用项目根路径，保留清单（`getSlimmerKeepList`，以 path 为键）因此天然按项目根粒度生效。不需要新的持久化键，不需要改 `addSlimmerKeepPath` 的调用点。

**为什么不用根内哈希或自增 id：** 路径跨扫描稳定且人类可读，失败时可"在访达中显示"直接指向它；哈希会让"未完整"标记无法关联。

### D7: 分组是呈现层，不是模型层

技术栈分组只存在于 UI 层（`smart_disk_slimmer_page.dart` 的呈现），`SlimCandidateItem` 只新增 `projectArtifacts` 分类值与聚合所需字段（产物明细列表、预算标记）。技术栈归属由产物名推导（`package.json` 信号 / `node_modules` / `dist` → Node；`pubspec.yaml` / `.dart_tool` → Flutter；`build.gradle` / `.gradle` → Gradle）。

**为什么不把分组写进数据模型：** 分组会随用户配置变化（例如只关心 Node），持久化分组会造成陈旧数据；推导式分组永远与当前信号一致。

## Risks / Trade-offs

- **[Tier B 总耗时超预期，4 阶段扫描被感知为变慢]** → 每个根 2–4s 预算 × 670 根理论上限极长，且实测 24% 的根在根目录层就命中产物，剪枝不会让工作量缩水。缓解：按根并发度受限的并行收集（复用 `_calcDirSize` 的 yield 节奏，不抢主 isolate）；列表按组渐进上抛，用户先看到组级汇总；规格要求超预算显式上报，不静默丢弃。实现期需要一次本机实测来校准预算数值，这属于可调参数而非规格决策。
- **[manifest 门控漏掉非工作区产物]** → 已知的、被接受的取舍（D2）。缓解：watchlist 豁免门控（D4），UI 在设置里明确说明"未在工作区内的产物需手动添加项目根"。
- **[聚合隐藏单目录风险]** → 用户看不到"到底会删哪个目录"。缓解：规格要求条目可展开查看每目录的 path 与 size；保留清单按根粒度生效，误判后只需标记一次。
- **[技术栈推导误分类]** → 一个根同时含 `pubspec.yaml` 和 `package.json`（monorepo）时归属哪组。缓解：按"最具体的信号"优先级判定（`.gradle`/`build.gradle` > `pubspec.yaml`/`.dart_tool` > `package.json`/`node_modules` > 其他），并在无信号时归入"其他构建产物"兜底组，不静默丢弃。
- **[配置迁移链路变长（旧文件 → clean-builds.json → 瘦身键）]** → 两步复制存在中间态丢失风险。缓解：迁移幂等且只执行一次；原文件不删（`settings-storage` 既有约束）；迁移失败走既有容错（损坏配置回退默认 + 可感知提示），不阻塞应用启动。
- **[最近使用重定向被用户误读为"工具改名"]** → 缓解：重定向是透明替换（记录里存 `smart-disk-slimmer`），侧边栏分组变化本身可解释；不显示"清理构建产物"这个已不存在的名字。

## Migration Plan

1. 实现 Tier A/B 检测器与规格要求的门控、预算、聚合、分组，先在瘦身工具内以隐藏方式验证，不改动注册表。
2. 实现配置迁移（`clean-builds.json` → 瘦身键），确认 watchlist 与产物开关可读、可作用。
3. 移除注册表条目与 `lib/clean_builds_tool.dart`，实现最近使用重定向。
4. 部署后验证：新扫描出项目产物组、旧 watchlist 生效、废纸篓回收可逆、`clean-builds` 旧文件仍在磁盘上。
5. **回滚**：git revert 即可。数据侧无需回滚——迁移是复制，`clean-builds.json` 原文件始终保留；新建的瘦身键条目回滚后不会被旧版读取，但也不污染旧版行为。构建产物删除走废纸篓，误删可从废纸篓恢复。
6. 部署前需在本机跑一次 Tier B 实测校准预算数值（风险 1 的缓解项）。

## Open Questions

- Tier B 的单根时间预算具体取 2s 还是 4s、产物数量上限取多少 —— 需要一次本机实测校准，不改变规格与任务分解。
- 技术栈分组是否要在 UI 上做成可折叠的组内 chip（进一步减少行数），还是保持"组行 + 展开明细"两层 —— 呈现细节，可在实现期按 670 根的真实列表高度决定。
- 无 manifest 也非 watchlist 的根内的产物是否需要一个"其他"兜底发现层 —— 目前不做（Non-Goal），若实测发现漏报比例高再立独立变更。
